# 第二章 2.5 传输层技术介绍 — PPT改进说明

## 一、原PPT问题分析

原PPT（传输层_v2.pptx，76页）存在以下问题：

1. **文字密度过高**：大量页面整页文字，如第4、5、6、8、9、10、11页等，每页300-500字，不符合教学PPT"少字多图"的原则。
2. **协议堆砌过多**：拥塞控制列举了8个协议（CODA、CCF、PCCP、Trickle、Fusion、Siphon、LACAS、ARCC），可靠传输列举了7个协议（ESRT、RMST、RBC、PSFQ、GARUDA、ART、CTCP），面面俱到但重点不突出。
3. **缺少图示**：大量纯文字描述流程，缺少流程图、示意图、对比表格等视觉元素。
4. **层次不清**：部分页面标题缺失（如第27、30、32页），过渡不自然。
5. **公式过多**：多处出现形式化定义和公式，不适合本科教学理解。

## 二、改进原则

1. **精简文字**：每页PPT正文不超过6-8行要点，详细解释由教师口述。
2. **突出核心协议**：拥塞控制重点讲CODA、Fusion；可靠传输重点讲ESRT、PSFQ。其余协议以对比表形式简要提及。
3. **增加图示**：为每个核心概念和协议配示意图。
4. **增加对比表**：用表格横向比较协议，帮助学生建立系统认识。
5. **减少公式**：去除形式化定义，用直观语言解释概念。
6. **总页数控制在约50页**，适配4课时200分钟。

**第16页 — WSN中拥塞产生的原因**
- 标题：WSN为什么更容易拥塞？
- 原因一：**漏斗效应（Funnel Effect）**
  - 示意图：多个源节点 → 汇聚 → Sink附近流量暴增
  ```
  S1 ─→ ┐
  S2 ─→ ├→ R1 ─→ ┐
  S3 ─→ ┘        ├→ Sink  ← 此处流量最大
  S4 ─→ R2 ─────→ ┘
  ```
  - 离Sink越近，负载越大
- 原因二：**突发流量**
  - 事件检测型应用：多个节点同时检测到事件 → 短时间内大量数据涌入
- 【改进说明】原PPT第19页精简，增加漏斗效应示意图

**第17页 — 拥塞的分类**
- 标题：拥塞的分类

|------|------|------|
| 节点级拥塞 | 数据到达速率 > 发送速率 | 队列溢出 |

**第25页 — CODA：开环反压机制**

**第26页 — CODA：闭环多源调整机制**
- 标题：CODA——闭环调整（长期解决）
- 工作流程：
  ```
  正常状态：Sink定期向源节点发送ACK（维持速率）
  拥塞持续：Sink停止发送ACK
  源节点未收到ACK → 降低发送速率（AIMD算法）
  拥塞缓解后：Sink恢复ACK → 源节点逐步提高速率
  ```
- AIMD算法简介：
  - **加性增（AI）**：无拥塞时，速率 = 速率 + α（线性增长）
  - **乘性减（MD）**：拥塞时，速率 = 速率 × β（β<1，快速降低）
- 【改进说明】原PPT第33页后半精简

- 标题：Fusion三层机制工作原理

  - 下游节点收到拥塞位 → 暂停转发

**第33页 — 端到端可靠 vs 逐跳可靠**
- 标题：端到端 vs 逐跳——两种可靠性实现策略
- 对比示意图：
  ```
  端到端可靠：
  源 ─────────────────→ Sink
  ←─────ACK/NACK──────
  (跨越多跳的反馈闭环)

  逐跳可靠：
  源 → R1 → R2 → R3 → Sink
     ←ACK ←ACK ←ACK
  (每一跳独立确认)
  ```
- 对比表：

| 特性 | 端到端可靠 | 逐跳可靠 |
|------|-----------|----------|
| 反馈延迟 | 大 | 小 |
| 能量开销 | 高（ACK多跳传输） | 低（ACK单跳） |
| 缓存需求 | 只在源端 | 每个中继节点 |
| WSN适用性 | 差 | 好 |

- 结论：WSN多采用逐跳可靠

**第34页 — 上行可靠 vs 下行可靠**

**第35页 — 丢包检测：ACK vs NACK**
- 标题：可靠性基础——如何发现丢包？
- 两种方式对比：
  ```
  ACK（发送者发起）：
  发送者发数据 → 启动定时器 → 超时未收到ACK → 判断丢包

  NACK（接收者发起）：
  接收者检查序列号 → 发现序列号不连续 → 发送NACK通知丢包
  ```
- 第三种：**隐式ACK**
  - 利用无线广播特性，发送者侦听下一跳是否转发了数据
  - 无额外开销
  - RBC协议采用
- 对比表：

| 方式 | 发起者 | 开销 | 适用场景 |
|------|--------|------|----------|
| ACK | 发送者 | 高 | 端到端确认 |
| NACK | 接收者 | 中 | 逐跳恢复 |
| 隐式ACK | 发送者 | 低 | 无线广播环境 |

**第36页 — 丢包恢复**
- 标题：丢包恢复——如何补救？
- 方法一：**重传**
  - 需要发送端缓存已发数据
  - 端到端重传 vs 逐跳重传
  - 逐跳重传效率更高（单跳距离）
- 方法二：**纠错编码（FEC）**
  - RS编码：m个原始包 → n个编码包（n>m）
  - 接收任意m个编码包即可恢复
  - 优势：不需要知道具体哪个包丢了
  - 示意图：
    ```
    发送4个编码包 → D1收到3个 → 可恢复
                 → D2收到3个 → 可恢复
    只需补发1个编码包（而非2个不同的原始包）
    ```
- 方法三：**冗余发送**
  - 同一数据多次发送
  - 简单但效率低
- 【改进说明】原PPT第54-55页合并精简

**第37页 — 核心协议：ESRT概述**
- 标题：ESRT——事件可靠传输协议
- ESRT全称：Event-to-Sink Reliable Transport
- 核心思想：
  - 不追求每个包都到达（不是数据包可靠）
  - 只要Sink收到足够多的包就能检测事件（事件可靠）
  - 通过调整全网报告频率来平衡可靠性和能耗
- 关键参数：
  - 观测可靠性 η = r/R（实际收到包数 / 期望包数）
  - 目标：维持 1-α ≤ η ≤ 1+α
- 【改进说明】原PPT第57页精简，去掉公式推导

**第38页 — ESRT：五种网络状态**

| 状态 | 拥塞? | 可靠性? | ESRT策略 |
|------|-------|---------|----------|
| (NC, LR) | 无拥塞 | 低可靠 | 提高报告频率 |
| (NC, HR) | 无拥塞 | 高可靠 | 降低频率（省能量） |
| (C, HR) | 拥塞 | 高可靠 | 乘性减降低频率 |
| (C, LR) | 拥塞 | 低可靠 | 指数减降低频率（最差状态） |
| **OOR** | **无拥塞** | **达标** | **保持当前频率（最优状态）** |

**第40页 — 核心协议：PSFQ概述**
- 标题：PSFQ——缓发快取协议
- PSFQ全称：Pump Slowly, Fetch Quickly
- 核心思想：
  - **缓发（Pump Slowly）**：源节点以较慢速率发送数据
  - **快取（Fetch Quickly）**：丢包节点以较快速率从邻居取回丢失的包
- 设计目标：下行可靠传输（Sink向节点分发代码/命令）
- 名字含义图：
  ```
  Pump Slowly:  Sink ──慢──→ R1 ──慢──→ R2 ──慢──→ 节点
  Fetch Quickly: 若R2发现丢包 → R2 ──快──→ R1（取回丢失的包）
  ```
- 【改进说明】原PPT第68页精简

**第41页 — PSFQ：三个操作**
- 标题：PSFQ的三个核心操作
- **① 发操作（Pump）**：
  - 源节点慢速注入数据包（带序列号）
  - 中继节点接收并缓存
  - 慢速发送避免拥塞
- **② 取操作（Fetch）**：
  - 接收者检查序列号连续性
  - 发现序列号不连续 → 发NACK请求邻居重传
  - 支持"丢失聚合"：一个NACK请求一组丢失的包
  - 多个邻居可能各持有不同的丢失包
- **③ 报告操作（Report）**：
  - 最远节点发起，沿路径回传送达状态
  - 中继节点在报告中附带自己的状态信息
  - Sink获得全网送达情况

**第42页 — PSFQ工作流程图**
- 标题：PSFQ工作流程示意
- 完整示意图：
  ```
  Sink(源) 发送包: P1, P2, P3, P4, P5（慢速）

  R1: 收到 P1, P2, P3, P4, P5 ✓（全部转发给R2）

  R2: 收到 P1, P2, __, P4, P5（P3丢失！）
  ```
