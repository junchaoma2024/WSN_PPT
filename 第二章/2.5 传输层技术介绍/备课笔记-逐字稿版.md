## 2.5.1 传输层概述与TCP回顾（50分钟）

### 一、协议栈回顾与传输层定位（5分钟）

同学们好，今天我们开始学习第二章的第五节——传输层技术介绍。

在正式开始之前，我们先回顾一下，到目前为止我们在第二章学了哪些内容。

2.1节我们了解了OSI参考模型和WSN的协议架构，建立了整体框架。2.2节学了物理层——信号怎么在无线信道中传输。2.3节学了MAC层——多个节点如何在共享信道上有序通信。2.4节学了网络层——数据如何从源节点通过多跳路由到达基站。

现在我们来到了协议栈的下一层——传输层。

传输层位于网络层之上，它的职责是为应用层提供端到端的数据传输服务。大家注意，网络层关心的是"怎么找到一条路"，把数据从A送到B。但网络层不关心两件事：第一，路上有没有"堵车"——也就是拥塞问题；第二，数据有没有"丢"——也就是可靠性问题。

这两件事就是传输层要解决的。简单说：

- **网络层**：负责"找路"（路由）
- **传输层**：负责"保质保量"（拥塞控制 + 可靠传输）

### 二、传输层的五大功能（5分钟）

传输层具体提供哪些功能呢？主要有五项：

**第一，传输连接管理。** 对于面向连接的传输服务，传输层需要在数据传输之前先建立端到端的连接。在传输过程中监控连接状态，传输结束后释放连接。就像打电话一样——先拨号建立连接，通话，然后挂断。

**第二，可靠数据传输。** 传输层要保证数据正确、有序地到达目的端。源端发出的数据，经过网络传输后可能会丢包、乱序、出错，传输层负责检测这些问题并修复。

**第三，拥塞控制。** 当网络中的数据流量超过了网络的承载能力，就会发生拥塞。拥塞会导致大量丢包和延迟增大。传输层需要及时检测拥塞并采取措施，避免网络崩溃。

**第四，流量控制。** 调节发送端的发送速率，使其与接收端的处理能力相匹配。发太快接收端来不及处理，发太慢浪费带宽。

**第五，多路复用。** 多个应用进程可以共享同一个传输层实体进行通信。

在这五个功能中，对于WSN来说，最核心的两个是**拥塞控制**和**可靠传输**。这也是我们本节课的两大主题。

### 三、WSN传输层的特殊需求（5分钟）

和传统网络相比，WSN对传输层提出了一些特殊的要求。为什么呢？因为WSN有几个特殊的挑战：

**第一，传感器节点的计算和通信能力有限。** 单个传感器只有很有限的处理能力和较短的通信范围。这意味着传输层协议不能太复杂，不能要求节点做大量的计算。

**第二，传感器由电池供能。** 能量用完就没了，所以节能至关重要。传输层协议的每一次重传、每一次确认都在消耗能量，必须精打细算。

**第三，无线信道不可靠。** 信号衰减、多径效应、信道衰落，这些都会导致数据在传输过程中出错或丢失。无线链路的丢包率远高于有线链路。

**第四，密集部署导致信道竞争和拥塞。** 大量节点部署在一起，都要使用同一个无线信道通信，竞争非常激烈，拥塞很容易发生。

这些挑战意味着：传统Internet的传输层协议（比如TCP）不能直接用在WSN中。我们需要专门为WSN设计的传输层协议。

下面我们先回顾一下TCP协议，看看它是怎么工作的，然后分析为什么它不适合WSN。

### 四、TCP协议回顾（20分钟）

#### TCP三次握手（5分钟）

TCP是传统Internet中最常用的传输层协议，它是一个面向连接的协议。什么叫面向连接？就是通信双方在传输数据之前，必须先建立连接。

TCP用三次握手来建立连接。假设有两个实体A和B：

```
第一次握手：A → B：SYN, seq=x
  A说："B，我想和你建立连接，我的初始序列号是x。"

第二次握手：B → A：SYN+ACK, seq=y, ack=x+1
  B说："好的，同意建立连接。我的初始序列号是y，我已经收到了你的x。"

第三次握手：A → B：ACK, seq=x+1, ack=y+1
  A说："收到，确认。"
```

三次握手完成后，连接建立，双方可以开始传输数据了。释放连接的过程类似，也是通过协商完成的。

为什么需要三次握手？因为双方都需要确认对方的接收和发送能力正常。两次不够——B不知道A是否收到了自己的确认；一次更不行——根本没有确认。三次是最少的、能确保双方同步的次数。

#### 确认重传与滑动窗口（7分钟）

连接建好了，怎么保证数据可靠传输呢？TCP用的是**肯定确认重传机制**。

最简单的方式是"停等机制"——发送端发一个数据包，然后等待。接收端收到后返回一个ACK确认。发送端收到ACK后才发下一个。如果超时没收到ACK，就认为丢包了，重传。

```
停等机制：
发送端：发包1 → 等ACK → 收到ACK → 发包2 → 等ACK → ...
```

这种方式很简单但效率很低——发送端大部分时间都在等待，信道利用率很低。

为了解决这个问题，TCP引入了**滑动窗口机制**。滑动窗口允许发送端在等待确认之前连续发送多个数据包。

```
滑动窗口机制：
发送端：发包1, 发包2, 发包3 → 收到ACK1 → 窗口滑动 → 发包4 → ...
```

窗口大小决定了发送端可以同时"在路上"的数据包数量。窗口越大，发送速率越快，信道利用率越高。当窗口第一个包被确认后，窗口向后滑动一格，可以发送新的包。

这就像一条流水线——不是做一个等一个检查完再做下一个，而是连续生产，同时检查。

#### 慢启动与拥塞避免（8分钟）

滑动窗口带来了效率，但也带来了一个新问题——如果窗口太大，发送速率太快，就可能导致网络拥塞。所以TCP需要控制窗口的大小。

TCP用两个变量来控制发送窗口：
- **rwnd（接收窗口）**：接收端告诉发送端"我的缓存还能装多少数据"
- **cwnd（拥塞窗口）**：发送端根据网络拥塞状况自己估计的窗口大小

实际的发送窗口取两者的较小值：发送窗口 = min(rwnd, cwnd)。

关键在于cwnd是怎么变化的。TCP用了一个非常经典的算法：**慢启动 + 拥塞避免**。

**慢启动阶段：** 连接刚建立时，cwnd从1个数据段开始（不是一下子就打满）。每收到一个ACK，cwnd就增加1个数据段。注意，这看起来是线性增长，但实际上每一轮发送后收到的ACK数量翻倍，所以cwnd是指数增长的。第一轮发1个包，第二轮发2个，第三轮发4个，第四轮发8个……增长很快。

为什么叫"慢启动"？因为它从1开始，而不是一上来就用很大的窗口。虽然增长速度是指数级的，但起点很低。

**拥塞避免阶段：** 指数增长不能一直持续，否则很快就会拥塞。TCP设了一个阈值**ssthresh**。当cwnd超过ssthresh后，增长方式从指数变为线性——每收到一轮ACK，cwnd只增加1个数据段。这样增长变慢了，试探着接近网络容量的上限。

**超时处理：** 如果发生超时（丢包），TCP认为网络拥塞了。此时：
- cwnd重置为1（重新慢启动）
- ssthresh设为发生拥塞时cwnd的一半

我给大家画这个经典的图：

```
cwnd
↑
│      /\
│     /  \    线性增长
│    /    ← ssthresh=16
│   / 指数增长
│  /
│ /
│/____________ 超时! cwnd=1, ssthresh=12
│ /
│/
└──────────────────→ 时间
```

这个机制让TCP能够自适应地调节发送速率——网络好的时候加速，拥塞的时候减速，找到一个平衡点。

### 五、TCP不适合WSN的原因（5分钟）

TCP在传统Internet中工作得很好，但它不适合无线传感器网络。为什么？有四个主要原因：

**第一，TCP假设链路是可靠的。** TCP是为有线网络设计的，有线链路的丢包率非常低（通常低于0.001%）。TCP把所有的丢包都当作是拥塞导致的——丢包了就降低发送速率。但在WSN中，无线链路的丢包率很高（可能达到5%-30%），丢包很可能是信道质量差导致的，不是拥塞。如果TCP每次丢包都降速，发送速率会被压到很低，根本没法正常工作。

**第二，TCP需要建立端到端连接。** 三次握手需要源节点和目的节点之间有可靠的来回通信。在WSN中，数据从传感器经过多跳到达Sink，中间节点可能随时因为能量耗尽而失效，建立和维护端到端的可靠连接非常困难。

**第三，TCP对资源的要求较高。** TCP需要维护连接状态、滑动窗口、重传缓冲区等，这些都需要内存和计算资源。传感器节点的资源非常有限，难以支撑TCP的开销。

**第四，TCP的通信模式不匹配。** TCP是为点对点通信设计的，而WSN是多对一的汇聚模式（多个传感器向一个Sink报告数据）。

我用一个表格来总结：

| TCP假设 | WSN实际情况 |
|---------|------------|
| 有线链路，丢包率极低 | 无线链路，丢包率高 |
| 丢包 = 拥塞 | 丢包可能是信道问题 |
| 端到端连接可靠 | 多跳路径不稳定 |
| 节点资源充足 | 节点资源极度受限 |
| 点对点通信 | 多对一汇聚通信 |

所以，我们需要专门为WSN设计的传输层协议。

这里我提一个问题让大家思考："TCP把丢包当拥塞处理，在WSN中会怎样？"

对，WSN中无线链路经常丢包，TCP会不断降低发送速率，结果就是发送速率越来越低，几乎无法传输数据。这就是TCP在WSN中"水土不服"的根本原因。

### 六、传输层协议评价指标（8分钟）

既然TCP不行，我们要设计新的协议。那么怎么评价一个WSN传输层协议好不好呢？主要有五个指标：

**第一，能量效率。** 这是WSN最关注的指标。丢包是影响能耗的主要因素——丢掉的包已经消耗了多跳传输的能量，而且还需要额外的能量来重传。好的协议应该尽量减少不必要的传输，减少丢包和重传。

**第二，可靠性。** 但这里的可靠性分两种：

**数据包可靠**——要求每个数据包都能成功到达目的端，一个都不能丢。什么应用需要数据包可靠呢？比如Sink向所有传感器节点分发新的程序代码，或者下发查询命令——每个节点都必须正确收到。

**事件可靠**——不要求每个包都到达，只要Sink收到足够多的数据包，能够检测到事件就行。什么应用只需要事件可靠呢？比如温度监测——一个区域10个传感器都在测温度，即使其中2个的数据丢了，Sink还是能从剩下8个的数据判断出这个区域的温度。

大多数WSN应用只需要事件可靠，不需要数据包可靠。这是一个非常重要的认识。如果我们过度追求数据包可靠，付出的重传代价会非常大。

**第三，公平性。** Sink希望来自每个节点的数据量大致相同，而不是某些节点的数据特别多、某些节点的特别少。离Sink远的节点，数据经过更多跳传输，更容易丢失，所以公平性需要特别关注。

**第四，及时性。** 协议要能快速响应网络状态的变化，比如及时发现拥塞、及时通知相关节点。如果响应太慢，等你发现拥塞的时候，大量数据已经丢了。

**第五，可扩展性。** 协议要能适应不同规模的网络。100个节点时能工作，1000个节点时也要能工作。

### 七、2.5.1小结与过渡（2分钟）

好，我们来回顾一下2.5.1节学了什么：

1. 传输层位于网络层之上，负责端到端的传输质量保障
2. 传输层五大功能，WSN最关心拥塞控制和可靠传输
3. TCP的核心机制：三次握手、滑动窗口、慢启动+拥塞避免
4. TCP不适合WSN的四个原因
5. WSN传输层协议的五大评价指标

下面我们进入第一个核心主题——拥塞控制机制。

## 2.5.2 拥塞控制机制（50分钟）

### 一、什么是拥塞？（5分钟）

什么是拥塞？我给大家打个比方。

想象一下早高峰的高速公路。正常情况下，车流量不大，大家都能以正常速度行驶。但到了早高峰，车流量激增，超过了道路的容量，结果是什么？堵车！车越来越多、越走越慢、甚至完全停滞。

网络拥塞也是一样的道理：

```
道路 ↔ 无线链路
车辆 ↔ 数据包
道路容量 ↔ 网络容量
车流量 > 道路容量 → 堵车
数据流量 > 网络容量 → 拥塞
```

拥塞的核心定义就是：**注入网络的数据流量超过了网络所能承载的容量。**

拥塞会导致三个严重后果：

第一，**有效吞吐率急剧下降。** 你以为发得越快收到的越多？错。拥塞后，丢包严重，实际有效传输的数据反而变少了。就像堵车后，整条公路的通行效率反而比不堵车时低得多。

第二，**丢包率显著增加。** 节点缓存满了，新来的包只能丢弃。信道冲突加剧，包在传输途中被破坏。

第三，**能量大量浪费。** 丢掉的包可能已经在网络中经过了好几跳传输，每一跳都消耗了能量。这些能量白白浪费了。而且重传丢失的包又需要额外的能量。

### 二、WSN拥塞产生的原因（5分钟）

WSN特别容易发生拥塞，主要有两个原因：

**第一个原因：漏斗效应（Funnel Effect）**

在数据收集型应用中，所有传感器节点的数据都向Sink汇聚。想象一下这个场景：

```
S1 → R1 ──→ ┐
S2 → R1 ──→ ├→ R3 ──→ Sink
S3 → R2 ──→ ┘
S4 → R2 ──→ ┘
```

离Sink越近的节点，负担越重。R3不仅要发自己的数据，还要转发R1和R2传来的所有数据。数据量像漏斗一样越聚越多。

即使每个源节点产生的数据量很小，经过汇聚后，Sink附近区域的数据流量也可能超过网络容量，导致拥塞。这就是漏斗效应。

**第二个原因：突发流量**

在事件检测型应用中，比如森林防火监测，平时数据量很小。但如果某个区域突然着火了，该区域附近大量传感器同时检测到高温事件，短时间内同时产生大量数据需要上报。这种突发的大流量很容易导致局部拥塞。

我给大家提个问题："假设有100个节点同时检测到火灾，全部开始向Sink报告数据，会发生什么？"

对，首先事件区域附近的信道竞争激烈，大量冲突导致链路级拥塞；其次数据汇聚到Sink方向，漏斗效应导致节点级拥塞。双重压力叠加，丢包率会非常高。

### 三、拥塞的分类（5分钟）

根据不同的标准，拥塞可以分为几类：

**按发生位置分：节点级拥塞 vs 链路级拥塞**

节点级拥塞是什么？就是某个节点接收数据的速度加上自己产生数据的速度，超过了它发送数据的速度。数据在节点的缓存队列中越积越多，最终队列溢出，新来的包只能丢弃。这和传统有线网络中的拥塞类似。

链路级拥塞是无线网络特有的。无线信道是共享的，当多个相邻节点同时尝试发送数据时，就会产生碰撞。碰撞导致数据包损坏，需要重传。重传又增加了信道负载，导致更多碰撞……形成恶性循环。

**重点：在WSN中，链路级拥塞是主要形式。** 研究表明，拥塞状态下因为信道冲突丢失的包，远多于因为队列溢出丢失的包。

**按影响范围分：局部拥塞 vs 全局拥塞**

局部拥塞由事件检测型应用造成——突发事件导致局部区域短时间内大量数据涌入，拥塞范围限于事件区域附近。持续时间通常较短。

全局拥塞由数据采集型应用造成——全网节点持续向Sink报告数据，由于漏斗效应，Sink附近区域持续拥塞。影响范围大，持续时间长。

### 四、拥塞控制三步骤——检测（12分钟）

好，知道了拥塞是什么、为什么发生、有哪些类型，下面关键问题是：怎么控制拥塞？

拥塞控制分为三个步骤，依次进行：

```
① 拥塞检测 → ② 拥塞通告 → ③ 拥塞解除
```

先讲拥塞检测——怎么发现网络拥塞了？

**方法一：基于队列长度的检测**

最直接的想法：如果一个节点的缓存队列越来越长，就说明进来的数据多、出去的数据少，可能要拥塞了。

基于队列长度的检测有三种具体方法：

第一种，**单一阈值法**。设定一个阈值，比如队列占满75%。当队列长度超过这个阈值，就认为发生了拥塞。CODA协议和Fusion协议用的就是这种方法。Fusion中，当节点队列剩余空间低于25%就认为拥塞。这种方法简单直接，但只能告诉你"有没有拥塞"，不能告诉你拥塞有多严重。

第二种，**队列增长率法**。不是看队列有多长，而是看队列长得有多快。如果按照当前的增长速度，下一个周期内队列就会溢出，那就判定要拥塞了。ESRT协议用了这种方法。它的优势是可以提前预警。

第三种，**多阈值法**。设定多个阈值（比如50%、70%、90%），每超过一个阈值就认为拥塞加重一级。这样不仅能检测拥塞，还能知道拥塞的程度——轻度、中度、重度。

基于队列长度的方法最大的优点是**实现简单、几乎没有额外开销**，所以是目前使用最广泛的方法。

**方法二：基于信道采样的检测**

队列长度反映的是节点自身的拥塞状况，但有时候信道本身就已经很拥挤了，队列还没来得及长起来。

基于信道采样的方法是：节点周期性地采样无线信道的状态——忙还是闲。统计信道忙的比例，如果这个比例超过了某个阈值，就说明信道接近饱和，可能要拥塞了。

CODA协议用了这种方法，而且提出了一个巧妙的优化叫"最小代价采样"。什么意思呢？只在节点有数据要发送时采样信道。因为CSMA协议本身就需要先听信道再发送，利用这个过程顺便采样，几乎不增加额外能耗。节点队列空了没数据要发，就停止采样。

基于信道采样比队列长度更精确，因为它直接反映了信道的使用状况。但缺点是需要MAC层支持，而且采样本身需要一定能量。

**方法三：基于端到端测量的检测**

前面两种方法都是在中间节点做的。第三种方法是在Sink做的。

Sink统计它收到的数据包的端到端传输延迟，或者统计丢包率。如果突然发现延迟明显增大，或者丢包率明显升高，就判断网络中某个地方发生了拥塞。

比如Siphon协议中，Sink持续统计来自各源节点的丢包率，如果连续10秒丢包率都超过40%，就判定网络拥塞。

这种方法的优点是：大部分计算都在Sink上做，Sink的资源通常比较充足，减轻了传感器节点的负担。缺点是：响应延迟大。Sink是在数据已经丢了之后才能发现拥塞的，不够及时。

**三种方法对比**

| 方法 | 检测位置 | 精度 | 开销 | 响应速度 |
|------|----------|------|------|----------|
| 基于队列长度 | 中继节点 | 一般 | 极低 | 快 |
| 基于信道采样 | 中继节点 | 高 | 较高 | 快 |
| 基于端到端测量 | Sink节点 | 高 | 低(节点端) | 慢 |

在实际应用中，可以同时使用多种方法来提高检测准确性。比如CODA就同时用了队列长度和信道采样两种方法。

### 五、拥塞控制三步骤——通告与解除（5分钟）

**第二步：拥塞通告**

检测到拥塞后，需要通知相关节点。有两种方式：

**显式通告**：发送专门的拥塞通知消息。好处是信息明确，可以携带拥塞程度等详细信息；坏处是需要额外的通信开销。

**隐式通告**：把拥塞信息嵌入到正常的数据包里。比如在数据包头部设置一个"拥塞位"（congestion bit）。如果拥塞了就把这个位设为1，邻居收到数据包后看到拥塞位为1就知道拥塞了。好处是不需要额外的消息；坏处是信息量有限，只能表示有没有拥塞，不能表示拥塞程度。

通告的方向也有两种：
- **反向通告**（向上游/源节点方向）：告诉上游节点"你发慢点"
- **正向通告**（向Sink方向）：告诉Sink"网络拥塞了"

**第三步：拥塞解除**

根据拥塞类型不同，解除策略也不同。

**局部拥塞的解除**：
- **反压（Backpressure）**：拥塞节点通知上游节点降低发送速率或暂时停止发送
- **丢包**：丢弃低优先级的数据包，保留重要的
- **数据融合**：在拥塞区域增大数据融合的力度，减少数据量

**全局拥塞的解除**：
- Sink计算一个合理的全网发送速率，洪泛通知所有源节点调整速率
- 或者只调整造成拥塞的子树上的节点速率（更公平）

### 六、核心协议：CODA（10分钟）

下面我们来学习第一个核心拥塞控制协议——CODA。CODA的全称是COngestion Detection and Avoidance，拥塞检测与避免。

CODA是WSN中最经典的拥塞控制协议之一，它包含三种机制：

**机制一：拥塞检测**

CODA同时使用队列长度和信道采样两种方法来检测拥塞。前面我们已经讲过了。通过最小代价采样来降低检测开销。

**机制二：开环跳段反压（短期应对）**

当一个节点检测到拥塞后，它立即向上游邻居广播一条反压消息："我这里拥塞了，请降低发送速率！"

```
源节点 → R1 → R2(拥塞!) → R3 → Sink

R2检测到拥塞：
R2 ──反压消息──→ R1
R1收到反压消息：
  → 降低自己向R2发送的速率
  → 或者缓存/丢弃部分数据
  → 判断自己是否也要继续向上游传播反压
```

上游节点收到反压消息后会降低发送速率或丢弃部分数据。如果上游节点本身也开始出现拥塞，它会继续向更上游传播反压消息。

这个机制是"开环"的——不需要端到端的反馈，每一跳独立决策，响应速度快，适合处理短暂的突发拥塞。

**机制三：闭环多源调整（长期解决）**

如果拥塞持续了很长时间，仅靠逐跳反压是不够的，需要从源头解决问题——让源节点降低产生数据的速率。

这时候闭环机制启动。正常情况下，Sink会定期向源节点发送类似ACK的反馈消息，维持源节点的发送速率。当Sink检测到持续拥塞时，它停止向相关源节点发送ACK。

源节点发现收不到ACK了——说明网络可能拥塞了，于是主动降低自己的发送速率。

速率调整使用的是经典的**AIMD算法**：
- **加性增（Additive Increase）**：没有拥塞时，速率缓慢线性增加。rate = rate + α
- **乘性减（Multiplicative Decrease）**：拥塞时，速率快速成倍降低。rate = rate × β（β<1）

这和TCP的拥塞控制思路是类似的——保守地增加、激进地减少，宁可少发一点也不要加剧拥塞。

CODA的三种机制配合工作：
- 拥塞检测快速判断
- 短暂拥塞用开环反压快速处理
- 持续拥塞用闭环调整从源头解决

### 七、核心协议：Fusion（5分钟）

第二个核心拥塞控制协议是Fusion。Fusion的特色是**跨层协作**——它不是只在一个层上工作，而是在网络层、应用层和MAC层三个层次同时控制拥塞。

**第一层：逐跳流量控制（网络层）**

当节点队列剩余空间低于25%时，该节点在发出的数据包中设置拥塞位（CB=1）。下游节点收到带有拥塞位的数据包后，暂时停止向这个方向转发数据，给拥塞节点时间来清空缓存。

**第二层：源速率限制（应用层）**

Fusion使用一种叫做**信令桶（Token Bucket）** 的算法来控制源节点的发送速率。父节点每向子节点发送一定数量的数据包，子节点就积累一个信令（Token）。子节点只有在信令数量大于0时才能发送自己的数据。信令用完就不能发了，必须等父节点再给。

这样，源节点的发送速率就被父节点间接控制了。

**第三层：优先级MAC访问**

通常CSMA协议给所有节点平等的信道访问机会。但拥塞的时候，我们希望拥塞节点能尽快把缓存中的数据发出去。Fusion让缓存中有待发数据的节点比缓存为空的节点拥有更高的信道访问优先级。

这三层机制协作的效果是：MAC层帮助拥塞节点尽快清空缓存，网络层的反压防止新数据继续涌入，应用层控制源头的数据产生速率。从下到上，全面控制。

### 八、其他协议简览与小结（3分钟）

除了CODA和Fusion，还有一些其他的拥塞控制协议。我用一个表格简要概括，大家了解即可：

| 协议 | 核心思想 |
|------|----------|
| CCF | 基于包服务时间调速，兼顾公平性 |
| PCCP | 基于优先级的拥塞度检测和速率调整 |
| Trickle | "礼貌流言"机制，适用于代码更新分发 |
| Siphon | 引入虚拟Sink节点，用多射频分流过载流量 |
| LACAS | 基于学习自动机，概率选择最优发送速率 |
| ARCC | 基于蚁群优化，信息素引导路径选择+拥塞避免 |

考试重点掌握CODA和Fusion就够了。

好，拥塞控制部分就讲到这里。我们回顾一下：

- 拥塞原因：漏斗效应 + 突发流量
- 拥塞分类：节点级/链路级、局部/全局
- 控制三步骤：检测（三种方法）→ 通告（显式/隐式）→ 解除（局部/全局）
- CODA：检测 + 开环反压 + 闭环AIMD
- Fusion：三层协作（逐跳流控 + 源速率限制 + 优先级MAC）

## 2.5.3 可靠传输机制（50分钟）

### 一、可靠性的多维度定义（8分钟）

同学们好，上节课我们学了拥塞控制——怎么防止网络过载。今天学传输层的第二个核心任务——可靠传输。

首先我们要明确一个问题：什么是"可靠"？在WSN中，可靠性的定义比你想象的要复杂。它不是一个简单的"可靠/不可靠"的二元概念，而是有多个维度。

**维度一：粒度——数据包可靠 vs 事件可靠**

这个上节课提到过。数据包可靠要求每一个数据包都必须成功送达目的端，一个都不能丢。典型场景是Sink向所有传感器分发新的程序代码——少一个字节程序就跑不起来。

事件可靠则宽松得多——只要Sink收到足够数量的数据包，能够可靠地检测到事件就行，允许一部分包丢失。典型场景是环境监测——100个传感器监测温度，即使丢了20个的数据，剩下80个足够让Sink判断出温度分布。

大多数WSN应用只需要事件可靠。这一点非常重要——如果你过度追求数据包可靠，付出的重传代价可能得不偿失。

**维度二：范围——端到端可靠 vs 逐跳可靠**

端到端可靠要求数据从源节点可靠地传输到最终的目的节点（Sink）。这需要源和目的之间建立闭环反馈机制——Sink收到数据后发回ACK，源节点没收到ACK就重传。

逐跳可靠只关注每一跳链路上的可靠传输。每个节点转发后只需要确保下一跳收到了就行。

这两种方式的区别：

端到端可靠：
- 反馈（ACK）需要从Sink经过多跳传回源节点，延迟大
- ACK本身也可能在多跳传输中丢失
- 重传也需要经过多跳，能量开销大
- 在WSN中实现代价太高

逐跳可靠：
- 确认只需要单跳，延迟小
- ACK丢失概率低
- 重传只需要单跳，能量开销小
- WSN中更实用

结论：**WSN多采用逐跳可靠**而非端到端可靠。

**维度三：方向——上行可靠 vs 下行可靠**

上行可靠是指从传感器到Sink方向的可靠性。这是数据收集的方向，多对一模式。由于传感器数据通常有冗余，上行一般只需要事件可靠。

下行可靠是指从Sink到传感器方向的可靠性。这是命令分发、代码更新的方向，一对多模式。由于每个节点都需要正确收到命令或代码，下行一般需要数据包可靠。

总结一下：

| 维度 | 分类 | 说明 |
|------|------|------|
| 粒度 | 数据包可靠 vs 事件可靠 | 每包到 vs 足够多包到 |
| 范围 | 端到端 vs 逐跳 | 源到目的 vs 单跳链路 |
| 方向 | 上行 vs 下行 | 传感器→Sink vs Sink→传感器 |

选择不同的可靠性级别，代价差别非常大。设计协议时，首先要明确应用到底需要什么级别的可靠性。

### 二、丢包检测方法（7分钟）

要实现可靠传输，第一步是发现丢包。怎么知道数据丢了？

**方法一：ACK（正面确认，发送者发起）**

这是TCP用的方法。发送端每发一个包就启动一个定时器，等接收端返回ACK。如果定时器超时了还没收到ACK，就判定丢包，重传。

超时等待时间通常设为一个RTT（往返时间）。设太短了会导致误判——可能包还在路上就被认为丢了；设太长了会导致响应太慢。

**方法二：NACK（否定确认，接收者发起）**

由接收端来检测丢包。接收端检查收到的数据包的序列号。正常情况下序列号应该是连续的：1, 2, 3, 4...。如果收到了1, 2, 4（少了3），就知道3号包丢了，然后向发送端发一条NACK消息："3号包没收到，请重传。"

NACK的优势是：如果没有丢包，就不需要发送任何确认消息——只有丢包了才发NACK。这比ACK（不管丢没丢都要回复）要节省带宽。

**方法三：隐式ACK**

这是利用无线广播特性的一种巧妙方法。

在无线网络中，一个节点发送数据时，它的邻居都能听到。所以如果节点A发数据给下一跳B，A可以继续监听信道。如果A听到B把这个数据转发给了B的下一跳，就说明B成功收到了——这就是隐式确认。不需要B额外发送任何ACK消息。

RBC协议就用了这种方法。

三种方法对比：

| 方式 | 发起者 | 额外开销 | 适用场景 |
|------|--------|----------|----------|
| ACK | 发送者 | 高（每包一个ACK） | 端到端确认 |
| NACK | 接收者 | 中（只在丢包时） | 逐跳恢复 |
| 隐式ACK | 发送者（监听） | 低（无额外消息） | 无线广播环境 |

### 三、丢包恢复方法（5分钟）

发现丢包后怎么办？有三种恢复方法：

**方法一：重传**

最直接的办法——丢了就重发。重传可以是端到端的（源节点重发）或逐跳的（丢包链路的上游节点重发）。

端到端重传的问题是：假设数据已经传了5跳，在第5跳丢了。端到端重传意味着源节点要重新发，数据又要走5跳。这5跳中前4跳其实之前已经成功了，现在白白重复一遍。

逐跳重传就高效多了：第4跳的节点缓存了这个数据，发现第5跳没收到，直接从第4跳重传一次就行了。只需要1跳的代价而不是5跳。

所以在WSN中，**逐跳重传比端到端重传高效得多**。代价是：中间节点需要缓存已发送的数据，占用存储空间。

**方法二：纠错编码（FEC，前向纠错）**

重传的问题是需要反馈——先发现丢了，再重传。有没有一种方法可以不需要反馈，直接容忍一定程度的丢包？

有的，就是纠错编码。最典型的是RS编码（里德-所罗门编码）。原理是：把m个原始数据包编码成n个编码包（n>m），接收端只要收到其中任意m个编码包就能恢复全部原始数据。

举个例子：4个原始包编码成6个编码包。即使丢了2个编码包，只要收到任意4个就能恢复原始的4个数据包。

这种方法特别适合一对多的下行传输。假设Sink向两个节点D1和D2发送4个包，D1丢了第1个包，D2丢了第4个包——它们丢的不一样。如果用重传，需要分别重传第1个和第4个，传两次。但如果用RS编码，只需要发一个额外的编码包，D1和D2各自结合自己收到的包就能恢复。

缺点是：编码计算开销较大，对传感器节点来说可能是个负担。

**方法三：冗余发送**

最简单粗暴的方法——同一个包发多次。即使其中一份丢了，还有备份。

优点：简单；缺点：效率低，浪费带宽和能量。

### 四、核心协议：ESRT（15分钟）

下面我们学习第一个核心可靠传输协议——ESRT。

**ESRT概述**

ESRT的全称是Event-to-Sink Reliable Transport——事件到Sink的可靠传输协议。

ESRT的核心理念是：**不追求数据包可靠，只追求事件可靠。** 它不关心每一个包有没有到达Sink，只关心Sink收到的包够不够多，能不能可靠地检测到事件。

ESRT用一个指标来衡量可靠性：

**η = r / R**

其中r是Sink在一个时间段内实际收到的数据包数量，R是Sink为了可靠检测事件所需要收到的包数量。η就是"归一化可靠性"。

ESRT的目标是：维持η在1附近。具体来说，维持 1-α ≤ η ≤ 1+α，其中α是一个容忍度参数。

如果η < 1-α，说明收到的包太少，可靠性不够。
如果η > 1+α，说明收到的包太多，虽然可靠性没问题但浪费了能量。
如果η在范围内，刚刚好。

ESRT怎么调整呢？通过控制全网的**报告频率f**——所有源节点的发送速率。

**ESRT的五种网络状态**

这是ESRT最核心的内容。ESRT根据两个维度把网络状态分为五种：

第一个维度：有没有拥塞（C=Congestion，NC=No Congestion）
第二个维度：可靠性高还是低（HR=High Reliability，LR=Low Reliability）

五种状态：

**状态1：(NC, LR)——无拥塞，低可靠**

什么意思？网络不拥塞，但Sink收到的数据包不够多。可能是因为源节点的发送频率太低了。怎么办？**提高报告频率**，让源节点发送更多数据。

**状态2：(NC, HR)——无拥塞，高可靠**

网络不拥塞，Sink收到的包太多了（超过了需求）。虽然可靠性没问题，但传感器在做无用功，浪费能量。怎么办？**降低报告频率**，省能量。

**状态3：(C, HR)——拥塞，高可靠**

网络拥塞了，但Sink收到的包还是足够多。说明数据发送过多，既造成拥塞又浪费能量。怎么办？**乘性减降低报告频率**，解除拥塞。

**状态4：(C, LR)——拥塞，低可靠**

这是最糟糕的状态。网络拥塞了，而且Sink收到的包不够。

这里有一个关键问题：拥塞且低可靠，应该提高频率（增加可靠性）还是降低频率（解除拥塞）？

答案是**降低频率**。为什么？因为当前网络已经拥塞了，如果提高频率会加剧拥塞，导致更多的丢包，可靠性反而更低。正确的做法是先解除拥塞，然后再慢慢提高频率。ESRT用**指数减**来快速降低频率。

**状态5：OOR——最优操作区域（Optimal Operating Region）**

这是ESRT追求的理想状态。网络不拥塞，可靠性恰好满足要求。此时**保持当前报告频率不变**。

ESRT的目标就是让网络达到并保持在OOR状态。

**ESRT的工作流程**

每个决策周期，ESRT做三件事：
1. Sink统计这个周期内收到的数据包数量，计算η
2. Sink检测是否拥塞（用队列增长率法）
3. 根据η和拥塞状况判断当前网络状态，计算新的报告频率f，洪泛到全网

```
决策周期开始
    │
    ↓
Sink统计收到的包数 → 计算η=r/R
Sink检测拥塞（队列增长率）
    │
    ↓
判断网络状态：
(NC,LR)→提高f  (NC,HR)→降低f  (C,HR)→乘性减f
(C,LR)→指数减f  OOR→保持f
    │
    ↓
Sink将新的f洪泛到全网
所有源节点调整发送速率
    │
    ↓
下一个决策周期
```

**ESRT的特点**

优点：
- 功能集中在Sink，传感器节点只需调整发送速率，负担小
- 同时兼顾了拥塞控制和可靠性保障
- 以事件可靠为目标，避免过度保障

缺点：
- 全网所有节点使用相同的报告频率，不保证公平性
- 如果拥塞只是部分路径造成的，全网降速会影响不相关的节点

### 五、核心协议：PSFQ（12分钟）

第二个核心可靠传输协议是PSFQ。

**PSFQ概述**

PSFQ的全称是Pump Slowly, Fetch Quickly——缓发快取。这个名字就概括了它的核心思想。

ESRT解决的是上行可靠传输（传感器→Sink），PSFQ解决的是**下行可靠传输（Sink→传感器）**。典型场景是Sink向全网传感器节点分发新的程序代码。

PSFQ的核心策略：
- **缓发（Pump Slowly）**：源节点（Sink）以较慢的速率发送数据包，避免一下子涌入太多数据造成拥塞
- **快取（Fetch Quickly）**：如果某个中间节点发现丢包了，它不等源节点重传，而是立刻以较快的速率从邻居节点那里"取回"丢失的包

这个策略很聪明。慢慢发减少了拥塞的可能性；一旦丢包了，就近从邻居快速恢复，不需要从源端重新来过。

**PSFQ的三个操作**

**操作一：发操作（Pump）**

Sink将数据（比如程序代码）分成多个数据包，每个包带有序列号和文件标识。然后以较慢的速率逐个发送。

中间节点接收到数据包后，先缓存在本地，然后按照同样的慢速率转发给下一跳。

慢速发送有两个好处：第一，避免拥塞；第二，给中间节点时间来缓存数据，为后续可能的丢失恢复做准备。

**操作二：取操作（Fetch）**

如果某个节点发现收到的序列号不连续——比如收到了包1、包2、包4，少了包3——它就知道包3丢了。

这时候它怎么做？向邻居发送一条NACK消息："我缺包3，谁有？"

邻居节点如果缓存中有包3，就以较快的速率发回来。"快取"就体现在这里——恢复的速度比正常传输速度快。

PSFQ还有一个巧妙的设计叫**"丢失聚合"（Loss Aggregation）**。在无线网络中，丢包往往是成组出现的——因为信道条件差，可能连续几个包都丢了。所以PSFQ允许一个NACK请求一组丢失的包，而不是每丢一个就发一个NACK。

另外，一个节点缺失的包可能分散在不同的邻居节点中——邻居A有包3，邻居B有包5。PSFQ支持从多个邻居分别取回。

如果NACK发出后没有得到响应（可能邻居也没有），节点会设定一个定时器，周期性地重复发送NACK，直到收齐所有包。

**操作三：报告操作（Report）**

数据分发完成后，需要向Sink汇报送达情况。

报告消息从距离Sink最远的目标节点开始，沿路径向Sink方向回传。路径上的中间节点在转发报告消息时，把自己的送达状态也附加进去。

当报告消息到达Sink时，Sink就知道了全网每个节点的数据接收情况。如果发现某些节点还缺数据，可以有针对性地重传。

我给大家走一遍完整的流程：

```
Sink发送5个包：P1, P2, P3, P4, P5（慢速发送）

R1节点：收到 P1, P2, P3, P4, P5 ✓ 全部转发给R2

R2节点：收到 P1, P2, __, P4, P5（P3丢了！）
  → R2向R1发NACK："我缺P3"
  → R1缓存中有P3 → 快速发给R2
  → R2补齐P3 → 继续转发给下游

终端节点：收到 P1, P2, P3, P4, P5 ✓

报告阶段：终端节点 → R2 → R1 → Sink（汇报送达情况）
```

**PSFQ的特点总结**

优点：
- 逐跳恢复，不需要端到端重传——就近从邻居取回
- 中继节点缓存数据，丢失恢复快
- 慢发避免拥塞，快取保证恢复效率
- 丢失聚合减少NACK数量

缺点：
- 需要中继节点缓存数据，占用存储空间
- 只适用于下行传输
- 对实时性要求高的应用，慢发可能延迟过大

### 六、其他协议简览与可靠传输小结（3分钟）

除了ESRT和PSFQ，还有一些其他的可靠传输协议：

| 协议 | 类型 | 方向 | 核心机制 |
|------|------|------|----------|
| RMST | 数据包可靠 | 上行 | 基于NACK，缓存/非缓存两种模式 |
| RBC | 数据包可靠 | 上行 | 无窗口块确认+区别化竞争控制 |
| GARUDA | 数据包可靠 | 下行 | 核心/非核心节点结构，分阶段恢复 |
| ART | 事件可靠 | 双向 | 将节点分为必要(E)和非必要(N)节点 |
| CTCP | 数据包可靠 | 上行 | 合作式，两级可靠性 |

大家了解即可，考试重点掌握ESRT和PSFQ。

现在我们来思考一个重要的问题：拥塞控制和可靠传输是什么关系？

它们是互补的：拥塞控制通过防止网络过载来减少丢包，可靠传输通过检测和恢复来弥补丢包。但它们也可能矛盾：可靠传输的重传增加了网络流量，可能反过来加剧拥塞。

所以好的传输层协议需要协调这两者。比如ESRT就同时考虑了拥塞和可靠性，在五种状态中综合决策。

## 附录：常见问题预备

### Q1：ESRT在(C,LR)状态下为什么降低频率而不是提高频率？
**A**：因为网络已经拥塞。提高频率会加剧拥塞，导致更多丢包，可靠性反而更差。正确的策略是先解除拥塞（降低频率），等网络恢复正常后再逐步提高频率来提升可靠性。这体现了"先治堵，再增量"的思想。

### Q2：为什么WSN多用逐跳可靠而不是端到端可靠？
**A**：三个原因：(1)端到端ACK需要多跳传输，延迟大且ACK本身可能丢失；(2)端到端重传需要数据从源头重新发送，经过多跳，能耗大；(3)逐跳可靠只需单跳确认和重传，延迟小、能耗低、更适合WSN。

### Q3：CODA的开环和闭环有什么区别？
**A**：开环是局部、快速的应对措施——拥塞节点通知上游邻居减速，不需要Sink参与，适合短暂突发拥塞。闭环是全局、彻底的解决方案——通过Sink停发ACK控制源节点速率（AIMD），适合持续拥塞。

### Q4：PSFQ为什么要"慢发"？直接快速发送不好吗？
**A**：快速发送会导致大量数据同时涌入网络，容易引起拥塞和丢包。慢发控制了注入网络的数据速率，减少拥塞的可能。而且慢发给了中间节点缓存数据的时间，一旦后续出现丢包可以就近快速恢复。

### Q5：Fusion和CODA的主要区别是什么？
**A**：CODA在单一层次（网络层/传输层）上工作，主要靠反压和速率调整。Fusion是跨层协作——网络层逐跳流控、应用层源速率限制、MAC层优先级访问，三层协同。Fusion的设计更系统化。
